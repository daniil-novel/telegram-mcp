# Модель безопасности

[English](security.md) · **Русский** · [README](../README.ru.md)

Unofficial Telegram MCP ограничивает работу локального аккаунта, но не обещает полной безопасности. Здесь разделены запреты, обеспеченные кодом, меры репозитория GitHub и ответственность подключённого клиента. Приватные сообщения и действия при инциденте — в [SECURITY.md](../SECURITY.md#по-русски).

## Поток данных и доверие

```text
Ваш терминал: локальные credentials и вход
        ↓
Локальная сессия + разрешённые чаты/действия
        ↓
Фиксированные MCP tools → защищённые RPC → Telegram
        ↓
Разрешённый текст/подписи/метаданные → MCP-клиент → модель/история
```

Credentials приложения и вход остаются локально. **Разрешённые сообщения, личные сведения и метаданные всё равно получает клиент.** Сам сервер не интегрирован с провайдером модели, но MCP-клиент может загружать/сохранять ответы. [Планируемый слой приватности](../README.ru.md#планируемый-слой-приватности) — будущая разработка, не готовая функция.

Сессия Telegram обладает полномочиями аккаунта. Чтение ограничено кодом, а не Telegram-issued scope. Копирование сессии в другой клиент обходит guard этого проекта. Доверенными считаются пользователь ОС, установленный Python/зависимости, MCP-клиент и проверенный maintainer исходный код.

## Что обеспечивает реализация

| Угроза или риск | Действующая мера | Оставшаяся граница |
| --- | --- | --- |
| Неожиданное изменение Telegram | Фиксированные инструменты чтения; точный allowlist классов MTProto, проверка вложенных обёрток и границ call/send | Изменённый код, взлом runtime или украденная сессия — вне этой защиты. |
| Запись не тому получателю | По умолчанию отключена; отдельные точные разрешённые ID; запрет имеет приоритет, ACL чтения также действует | После включения разрешённый клиент способен запросить настроенную запись. Сервер сам не доказывает подтверждение каждого вызова человеком. |
| Редактирование/удаление чужих сообщений | Проверка собственных исходящих сообщений; ограничение количества ID и правки простого текста | Удаление может быть необратимым; Telegram также применяет свои права. |
| Дополнительные возможности записи | Точная ограниченная форма запроса: без медиа, планирования, impersonation, платных отправок и произвольных RPC | Новая возможность требует проектирования и тестов; одни аннотации — лишь подсказки. |
| Подмена cursor/области поиска | HMAC пагинации привязан к запросу/ACL и процессу | Cursor не обезличивает и не шифрует хранилище. Перезапуск делает его недействительным. |
| Раскрытие сессии/конфига | Скрытый интерактивный вход; внешнее хранение сессии; права/владелец файлов; Windows DPAPI; запрет symlink/junction | Сессии Linux/macOS не зашифрованы на диске. `.env` и данные сессии в памяти чувствительны. |
| Чужой HTTP-доступ | Bearer до MCP-вызовов; явные Host/Origin; loopback по умолчанию; предел тела запроса | Владельцы bearer разделяют права одного аккаунта. Это не разграничение пользователей, TLS или публичный OAuth-сервис. |
| Prompt injection в переписке | Ответы отмечены `content_is_untrusted=true`; сервер/skill предупреждают о тексте/названиях/подписях; ACL/RPC действуют | Метки/инструкции рекомендательны, не являются полным детектором. Клиент способен неверно использовать данные, другие инструменты или запись. |
| Секреты в ошибках | MCP-ошибки валидации/неожиданного backend используют диагностику без значений; input-модели скрывают значения в строках ошибок; журналы тихие | Успешное разрешённое чтение намеренно возвращает текст/метаданные. Сторонний клиент и отладка имеют отдельные риски утечек. |
| SQL/команды в сообщениях | Нет SQL query backend, `eval`, shell-исполнения или URL-fetching tool для содержимого; сессия — Telethon `StringSession` | Исполнение текста downstream-клиентом создаёт его собственную границу. Здесь SQL-подобный текст — обычные данные. |
| Нежелательная фоновая работа | Нет фоновых обновлений сообщений, мониторинга, read receipts и уведомлений рабочего стола | Клиент, браузер или другая интеграция способны создавать уведомления и сохранять историю. |

ACL чтения фильтрует MCP-ответ и адресные запросы. При получении списка диалогов метаданные/последние сообщения запрещённых чатов могут попасть в память backend. Если это существенно, используйте отдельный Telegram-аккаунт.

Реализация: [guard.py](../src/telegram_readonly_mcp/guard.py), [service.py](../src/telegram_readonly_mcp/service.py), [server.py](../src/telegram_readonly_mcp/server.py), [security.py](../src/telegram_readonly_mcp/security.py). Проверяйте именно устанавливаемую ревизию.

## Безопасное использование

- Начните со stdio, чтения и минимального необходимого allowlist. Учитывайте, кто видит ответы модели/историю клиента.
- Не отправляйте данные входа, сессии и `.env` в чат, issue, PR, скриншоты и общие/облачные папки. Используйте описанную локальную команду `protect-env`.
- Включайте запись только для конкретных получателей; перед подтверждением проверяйте чат, точный текст и действие. При неизвестном исходе читайте адресную историю до решения о повторе.
- По возможности оставляйте HTTP на loopback. Удалённому развёртыванию нужны защищённый транспорт, firewall и контроль вызывающих; токен не изолирует пользователей.
- Не запускайте неизвестный fork/ветку на своём аккаунте. Virtualenv изолирует пакеты, а не доступ к файлам/сети. Нужна одноразовая среда без настоящих credentials.

## Проверка репозитория и автоматизация

Публичность разрешает клонирование/fork, но не даёт права записи в исходный репозиторий. Процесс: **fork → отдельная ветка → PR в `main`**, см. [CONTRIBUTING.md](../CONTRIBUTING.md#по-русски). Слияние и изменение настроек GitHub доступны авторизованным maintainer. Защита исходного проекта не делает все публичные fork безопасными для запуска.

Включены GitHub secret scanning/push protection, Dependabot alerts/security updates и private vulnerability reporting. Generic non-provider secret patterns GitHub не включены; нестандартные/произвольные Telegram credentials могут избежать provider-pattern проверки. Workflow внешних участников требуют разрешения; default Actions token имеет права чтения, одобрение PR через Actions отключено.

[CI workflow](../.github/workflows/ci.yml) выполняет тесты без аккаунта, lint, форматирование и build на Windows/Linux/macOS. Конфигурация не доказывает успешный запуск: проверяйте результат нужного commit в [Actions](https://github.com/daniil-novel/telegram-mcp/actions) и [подтверждение проверок](../VALIDATION.md). Реальные Telegram-записи и личная переписка не должны попадать в fixtures или secrets CI.

### Main и ветки исходного репозитория

Три активных GitHub ruleset разделяют исключение для review и обязательные checks:

- [Основные правила main](https://github.com/daniil-novel/telegram-mcp/rules/24572891): изменение через PR, обязательные checks, актуальная ветка, закрытые обсуждения и линейная история. Force push/удаление запрещены. **Bypass не настроен ни для кого**, включая владельца, в этом ruleset.
- [Правила review main](https://github.com/daniil-novel/telegram-mcp/rules/24572892): одно одобрение code owner, устаревшее после изменений снимается. Назначенный reviewer — **@daniil-novel**. У владельца есть **исключение для review только через PR**, чтобы слить собственный maintenance PR после основных checks.
- [Другие исходные ветки](https://github.com/daniil-novel/telegram-mcp/rules/24572895): создание/изменение/удаление разрешено maintainer. Участники работают в fork; правила не управляют ветками чужого fork.

PR участников должны получать review владельца. GitHub привязывает исключение к maintainer, а не к автору PR; оно предназначено для собственных PR владельца. Оно не отменяет отдельные основные правила и не разрешает прямой push в `main`. Независимый review вторым человеком собственных изменений владельца не заявляется.

Правила/настройки хранятся на сервере и не копируются clone. Администратор может их менять; взлом аккаунта владельца или авторизованное изменение настроек — вне этой защиты. Проверяйте [актуальные правила](https://github.com/daniil-novel/telegram-mcp/rules), checks нужного commit и подтверждение результатов. Автоматические проверки не доказывают уместность желаемого изменения поведения.

| Проверка | Область | Ограничения |

| pip-audit 2.10.1 | Экспорт runtime/dev/scanner-зависимостей с хешами, на Windows/Linux | Известные опубликованные advisory; действуют platform markers, неизвестные уязвимости не обнаруживаются. |
| Gitleaks 8.30.1 | Достижимая история Git; стандартные шаблоны + [Telegram API hash/StringSession](../.gitleaks.toml); находки скрыты в диагностике | Ограниченные шаблоны/контекст; произвольные пароли и личные данные могут пройти. Binary DPAPI надёжно не покрывается. |
| actionlint 1.7.12 | Конфигурация GitHub workflow | Ошибки workflow, не доказательство надёжности action/зависимости. |
| Dependency review | Изменения зависимостей в PR; блокировка известных advisory от low severity | Известные advisory и поддерживаемый граф зависимостей; не анализ поведения runtime. |
| CodeQL | Python и Actions, `security-extended`, build mode `none` | Настроенные статические запросы; не проверяет реальный Telegram-аккаунт, смысл prompt и все раскрытия PII. |

Конфигурация: [security.yml](../.github/workflows/security.yml), [codeql.yml](../.github/workflows/codeql.yml). Actions закреплены на commit, права ограничены; у CodeQL analysis есть `security-events: write` для загрузки результатов. Обычные CI jobs не получают Telegram/model secrets. Аудит сверяет [экспорт с хешами](../security-requirements.txt) с `uv.lock` и проверяет его без установки экспортированного набора зависимостей.

Python-команды — в [CONTRIBUTING.md](../CONTRIBUTING.md#3-проверки-без-аккаунта). Если указанные native tools установлены из [Gitleaks releases](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1) и [actionlint releases](https://github.com/rhysd/actionlint/releases/tag/v1.7.12), выполните из корня:

```text
gitleaks git --no-banner --redact=100 --config .gitleaks.toml --log-opts="--all" .
actionlint
```

Наличие check или badge не доказывает успешный результат; проверяйте запуск нужного commit. Не отключайте checks, не игнорируйте необъяснённые находки и не вводите широкие allowlist ради зелёного PR.

## Чего не обещают сканеры

Статический анализ и поиск секретов выявляют часть опасного кода, известных форматов credentials и уязвимых зависимостей. Они не гарантируют отсутствие ошибок, вредоносного намерения, произвольных паролей, личных данных и prompt injection. SQL-строка в Telegram не является SQL injection этого сервера; важно, начинает ли какой-либо компонент исполнять её как код.

Синтетические тесты проверяют обеспеченные границы. Они не доказывают ноль утечек во всех библиотеках, средах, клиентах и будущих изменениях. Тихие журналы и общие ошибки снижают случайное раскрытие, но отладка, вывод сторонних компонентов и пользовательский текст ошибки требуют проверки. Не публикуйте исходную диагностику.

Изменения зависимостей/CI требуют такой же проверки, как runtime: установка пакета и workflow исполняют код. Читайте diff, lock, workflow permissions и ревизии actions до разрешения запуска/слияния. Не выдавайте Telegram/model credentials недоверенным PR jobs. См. [рекомендации GitHub для безопасных workflow](https://docs.github.com/en/actions/reference/security/secure-use).

Результаты релиза и непроверенные сценарии — в [VALIDATION.md](../VALIDATION.md). О подозрении на обход/раскрытие сообщайте через [приватную форму](https://github.com/daniil-novel/telegram-mcp/security/advisories/new) с вымышленным воспроизведением.
